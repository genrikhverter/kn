# 03-logic. KuSimulation — симуляция (`Simulation.lsf`)

> Модель — `02-data-model.md` §9. Источник — СТ модуль «Симуляция»
> (5 функций + сценарный анализ). Статусы: жизненный цикл/публикация —
> П; агрегация входа — У; модель — У (⚠ упрощение); сценарный анализ —
> У; выявление отклонений — К (справочник).

## 1. Константы модели (`ModelCoeff`)

Класс-справочник (вводится в этом модуле, от 02 отличии — зафиксировать
при генерации): `code STRING[40]` (уникальный), `value DOUBLE`,
`description`. Сид-значения: `baseTempN 'базовая t° N' = 8`,
`gddToHarvest = 1500`, `biomassMaxT = 12` (т/га), `stressLossPct = 30`.
Потребители: KuYield-калибровка.

## 2. Жизненный цикл задач (ФТ: управление ЖЦ)

- Суточное создание: задача планировщика `kuSimDaily()` (01:00):
  FOR полей с `currentCrop` и утверждённым планом: `NEW SimTask {
  planned <- сегодня 01:00; taskKind <- planned; horizon <-
  до конца сезона (30.09 − сегодня, max 1) }` — прототип: horizon 90.
- `runSimTask (SimTask t)`: статус → processing; сборка входа (ФТ
  агрегации): культура/сорт поля, дата сева (прототип: `sowDate`-поле
  Field отсутствует — берём 15.04 либо из сезонной карты, ⚠ допущение),
  агрохимия (последний SoilAnalysis), GDD-база; ошибки входа (нет
  культуры/агрохимии) → status=error + errorReason.
- Выполнение — модель **KuGDD-1.0** (⚠ допущение прототипа, по мотивам
  `Agro.lsf:229`):
  FOR дат от сева до сева+180 с шагом 1 день (кап 180 точек; для
  horizon-задач — от сегодня до +horizon):
  `gddDay = max(0, tDay − baseTempN)`, где `tDay` — среднемесячная
  температура-константа по месяцу (сид-таблица `MonthTemp`):
  апр 10, май 16, июн 21, июл 24, авг 23, сен 17 (⚠ допущение);
  накопительно `gddSum`; фаза: <30% `gddToHarvest` → 'Всходы' и т.д.
  (коды BBCH: 10/30/60/90);
  `biomass = biomassMaxT × min(1, gddPct)^1.5 × (1 − стресс)`;
  `ndvi = 0.2 + 0.6 × min(1,gddPct)`; `waterUse = et0-константа 4
  мм/день × коэф.фазы`; N/P/K-потребление = biomass × вынос/1000;
  `yieldForecast = targetYield(культуры) × min(1, gddPct)`.
- Завершение: `finishSimTask`: NEW SimResult + точки (SimResultPoint
  по дням; кап: точки каждые 3 дня, чтобы строк было ≤60), status →
  done, finishedAt. «Публикация» (СТ: сохранение и публикация) =
  SimResult.status='active' + `Field.currentPhase`-подсказка для
  коррекций (KuYield §5 берёт фазу отсюда).
- `cancelSimTask`: queued/processing → cancelled.

## 3. Сценарный анализ

`runScenario (ScenarioRun r)`: как §2, но модификация входа по
`scenarioKind` (⚠ допущения):
- fertilizing: +`pDose` кг д.в. в `pAppDate` → biomass-буст +5%;
- drought: `pStartDate..+pDays` → waterUse=0, biomass −`stressLossPct`%
  за каждый день >10 (кап 50%);
- irrigation: +`pIrrMm` в дату → снятие водного стресса;
- pest: с даты −`pPestPercent`/100 × biomass;
- sowDate: сдвиг кумулятивного GDD на разницу дат.
Результат → SimResult {forecastKind=scenario} связывается с r.result;
сравнение с базовым — форма «Базовый vs Сценарный» (Δ урожайности).

## 4. Выявление отклонений (К)

Реальный сервис — 05. Прототип: справочник StressType + действие
`registerStress (Field f, StressType s)` — ручная регистрация стрессу
агрономом (кнопка на карточке поля) → сразу создаёт
CorrectionRecommendation (KuYield §5). Автоматические триггеры
(по датчикам/NDVI) — 05.

## 5. Валидации

horizonDays 1–365;_scenarioRun: ровно один сценарий имеет параметры
(CONSTRAINT по kind); точки результата (result, pointDate) уникальны;
SimResult создаётся только завершённой задачей.

## 6. Сид

2 выполненные задачи (пшеница «Северное-1», кукуруза) с базовыми
результатами (точки каждые 3 дня), сценарный прогон «Засуха 14 дней»
(−18% урожайности — контрольный пример), справочник StressType
(засуха, заморозок, дефицит N, вредители, болезни).

## 7. Критерии приёмки

1. kuSimDaily создаёт по задаче на активное поле (повторный запуск не
   дублирует — guard).
2. runSimTask: без культуры → error + причина; нормальный прогон даёт
   SimResult с ≤60 точками, статус active.
3. GDD-инвариант: сумма gddDay по фиксированному ряду температур
   сходится с ручным расчётом.
4. Сценарий «Засуха 14 дней» даёт прогноз ниже базового.
5. registerStress приводит к рекомендации (сквозной сценарий
   симуляция → коррекция).
