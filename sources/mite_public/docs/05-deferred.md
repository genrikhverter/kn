# 05. Отложенная функциональность и ограничения прототипа

> «Что не можем / не делаем в прототипе» — требование заказчика:
> делаем то, что можем, остальное фиксируем документально. Для каждого
> пункта: требование СТ → причина → что вместо этого в прототипе →
> что потребуется в промышленной версии. Ссылки на статусы — `01-scope.md`.

## 1. Платформенные и архитектурные отступления

### 1.1. Реализация модулей 1–2 на 1С:Предприятие 8
- **Требование СТ**: модули «Планирование и бюджетирование» и
  «Земельные ресурсы» — расширения конфигурации 1С.
- **Причина**: прототип делается на LSfusion/MITE; дублирование на 1С
  противоречит цели прототипа.
- **В прототипе**: полные функциональные аналоги в Ku*.
- **Для промышленности**: перенос логики в 1С или пересогласование ТЗ;
  LSfusion-часть тогда — интеграция (обмен планами/бюджетами).

### 1.2. SPA-портал (UI-001–005, 301–505 в части SPA) и UI-Kit
- **Требование СТ**: React-SPA с централизованным UI-Kit, «36 форм
  превращаются в целостный интерфейс».
- **Причина**: веб-клиент LSfusion — генерируемые формы; SPA —
  отдельный фронтенд-стек.
- **В прототипе**: штатный веб-клиент MITE + навигатор `ku` (04-ui);
  для будущих SPA подготовлены REST-ручки (`/exec?action=Ku.*`).
- **Для промышленности**: React/Vue-фронтенд поверх REST API;
  OpenAPI-контракты (в СТ сами помечены «взгляд нейросети» —
  проектировать с нуля).

### 1.3. Мобильные приложения (UI-801/802) и офлайн-режим
- **Требование СТ**: Android/iOS-приложения полевого скаутинга и
  мониторинга техники с офлайн-накоплением и GPS/камерой.
- **В прототипе**: отсутствуют; регистрация стрессов — кнопкой в
  веб-клиенте (`registerStress`).
- **Для промышленности**: нативные/кросс-приложения + Sync-Engine;
  паттерн интеграции с внешним мобильным клиентом в MITE есть
  (`ExternalApp`, TSD-терминалы).

### 1.4. Offline-First, Агро-узел (Edge), Sync-Engine
- **Требование СТ** (архитектурные ограничения модуля 1): локальный
  кэш севооборота на краю, асинхронная синхронизация.
- **В прототипе**: центральный сервер, онлайн-валидация.
- **Для промышленности**: edge-кэш и очередь синхронизации вне
  LSfusion (сервер-центричен).

## 2. Данные и интеграции

### 2.1. ETL/ELT-конвейеры и Airflow (ФТ.ETL.1–2)
- **В прототипе**: расчёты напрямую в логике LSfusion, «витрины» —
  SQL view (`ku_v_*`, см. 03-logic KuAnalytics).
- **Для промышленности**: Airflow/DAG, staging, карантин записей,
  инкрементальные загрузки по маркерам.

### 2.2. DWH и SCD2-витрины (ФТ.DWH.1–6)
- **В прототипе**: операционная БД Postgres (PostGIS) MITE.
- **Для промышленности**: отдельное хранилище (Dimension/Fact/DataMart
  по логической модели СТ).

### 2.3. Событийная шина данных
- **Требование СТ**: бизнес-события («Сценарий цен утверждён», «Урожай
  учтен», «Коррекция утверждена») в шину.
- **В прототипе**: ServiceLog-журнал; REST-ручки по запросу.
- **Для промышленности**: Kafka/RabbitMQ; топики и форматы спроектировать.

### 2.4. Внешние реестры и ФЛК строгие
- Госреестр сортов, ФГИС «Зерно»/«Сатурн», ЕГРН, ФИАС: загрузки нет;
  ИНН/СНИЛС/ОГРН — только форматно-длина, без контрольных сумм ФНС;
  кадастровый номер — упрощённая маска. Полная валидация и интеграции —
  в промышленности.

### 2.5. Шифрование персданных и audit-trail (ФЗ-152)
- Контрагенты-физлица (паспорт, СНИЛС, дата рождения) хранятся
  открыто, история изменений — только даты создания/правки.
- Промышленность: шифрование полей, полный audit-log, оптимистические
  блокировки (поле «версия записи» СТ).

### 2.6. Версионирование записей справочников СТ
- СТ требует автоинкремент версии записи и таймштампы на каждый
  справочник; в прототипе — created/createdBy + status; версионирование
  документов (план/ТК/сценарий) — полноценно.

### 2.7. Импорт из файлов (CSV/XLSX/GeoJSON/KML)
- UI-106 (агрохимия), UI-202 (цены): в прототипе ручной ввод + сид.
- Промышленность: платформенный импорт lsFusion (IMPORT) — несложно,
  но вне скоупа прототипа.

## 3. Вычисления и модели

### 3.1. VRP-оптимизация графика обеспечения (ФТ4.4.1)
- **В прототипе**: эвристика-расписание (03-logic KuYield §7) без
  маршрутизации и целевой функции.
- **Для промышленности**: солвер (OR-Tools и т.п.) как внешний сервис;
  LSfusion — постановка/очередь/результат.

### 3.2. Имитационная модель роста (DSSAT/APSIM-класс)
- **В прототипе**: KuGDD-1.0 — упрощённая GDD-модель (⚠ помечено в
  03-logic KuSimulation; все константы в ModelCoeff для замены).
- **Для промышленности**: научная модель (собственная или интеграция
  DSSAT/APSIM), генетические коэффициенты культур из НСИ.

### 3.3. LLM-обоснования (калибровка ФТ4.3, коррекции ФТ4.2)
- **В прототипе**: сессия калибровки — каркас с ручными предложениями;
  тексты рекомендаций — шаблонные.
- **Для промышленности**: интеграция LLM (промпты, снимки данных,
  аудит токенов — сущности СТ готовы в 02 §8 как описание).

### 3.4. Методики-допущения (⚠ требует уточнения агрономом/экономистом)
Перечень всех допущений прототипа с точками вхождения:
- балансовая формула NPK и пересчёт запасов (03-logic KuYield §1);
- базовые влажность 14%/сорность 2% зачётного веса (KuProdPlan §2);
- распределение по месяцам МТР/БДР (KuBudget §2–3), ФОТ-ставка,
  связка «культура→продукция» через группу номенклатуры;
- сдвиги БДДС по условиям оплаты (KuBudget §4);
- среднемесячные температуры GDD-модели (KuSimulation §2);
- доля спасения урожая 30% в экономике коррекций (KuYield §5).

## 4. UI и аналитика

### 4.1. Картографический движок (UI-105, ФТ.GEO)
- В прототипе: таблицы с координатами + внешние ссылки на ПКК/OSM.
- Промышленность: Leaflet/MapLibre CUSTOM-компонентом (паттерн
  agro3d.js) + PostGIS + NDVI-слои/треки из DWH.

### 4.2. Конструктор отчётов self-service (UI-501, ФТ.REP)
- В прототипе: фиксированные Jasper-отчёты + Grafana.
- Промышленность: BI-инструмент (Grafana/Superset/Metabase) поверх
  витрин DWH или собственный конструктор.

### 4.3. Распределённый трейсинг (UI-603)
- В прототипе: SystemEvents/ProcessMonitor платформы.
- Промышленность: OpenTelemetry-контур.

### 4.4. Цветовая подсветка ячеек
- Формы СТ требуют подсветку (жёлтый/красный). Прототип — маркеры-
  символы + фильтры; фоны — если платформа поддерживает (04-ui §3).

## 5. Файлы и хранилище

- Файлы-предписания: JSON в БД вместо SHP/ISO-XML + S3 (ФТ4.1.4).
- Сканы/выписки (RAWFILE) — в БД; S3-хранилище — промышленность.
- REST API СТ (URL-структура `/api/planning/...`) — заменены на
  платформенные `/exec?action=...` (контракты СТ сами помечены как
  сгенерированные нейросетью).

## 6. Роли

- Ролевая модель СТ (5 ролей) — заглушка в СТ без матрицы прав;
  в прототипе — 4 признака ролей + SHOWIF (04-ui §5). Матрица
  «роль×форма×данные» — согласовать с заказчиком для промышленности.
